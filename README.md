# StringArtGenerator
Web based string art generator

This project is heavily based on the work of reddit user /u/kmmeerts from his post: https://www.reddit.com/r/DIY/comments/au0ilz/made_a_string_art_portrait_out_of_a_continuous_2/
Fork of halfmonty's work at https://github.com/halfmonty/StringArtGenerator

To use the original circle generator, navigate to: https://halfmonty.github.io/StringArtGenerator/

This version includes a rectangle generator at https://greyphilosophy.github.io/StringArtGenerator/.

## Rectangular frames

1. Select **Rectangle** and set the horizontal and vertical pin counts.
2. Upload an ordinary image. Its full width and height are preserved, with the longest side processed at 500 pixels. Landscape, portrait, and square images are supported.
3. Use a frame with the same width-to-height ratio as the image. To fit an existing frame, crop the image to that ratio before uploading; do not squeeze or stretch it. Pin counts control spacing, not the frame's proportions.
4. Copy the **entire saved instructions text**, including the frame settings, to keep your pattern. Paste it back later and choose **Start Creating** or **Just Draw**; no image upload is needed.

The previews and creation assistant preserve the same proportions as the generated pattern. Circle mode still center-crops the source to a square and uses a circular frame.

Rectangle pin numbering retains the original order: along the bottom from left to right, up the right side, along the top from right to left, and down the left side. Each side's count includes both corners. A shared corner therefore has two consecutive pin numbers referring to the same physical nail (the bottom-left corner uses the last number and 0). The number of distinct nails is `2 * horizontalPins + 2 * verticalPins - 4`.

New saved patterns include shape, processing dimensions, pin counts, and the sequence in JSON. Old comma-separated sequences still work: select their original shape and pin counts before playback. Old rectangle sequences have no aspect-ratio metadata and are displayed as squares, as before. Previously pre-squeezed source images should be replaced with the original images when generating a new rectangle pattern.

## Tests

Run `node --test tests/*.test.cjs` with Node.js 18 or newer. No dependencies are required. The tests execute the page's JavaScript with strict canvas and numerical doubles, covering landscape/portrait/square generation, circular cropping, pixel bounds, saved-pattern replay in a fresh session, navigation boundaries, legacy sequences, and invalid settings. These tests do not replace a browser smoke test with the real NumJS/OpenCV libraries.

## Automatic color plans

Select **Automatic colors**, choose a maximum of **1–5 colors** (default 5), and upload your original image. The generator recommends approximate thread swatches and a winding order. There is no manufacturer catalog to match and no purchasing action. Simpler images may produce fewer colors.

The default **Background** is **Transparent (open frame)**. Empty spaces are gaps, so both light and dark areas need thread; a white source image now calls for white thread. A fully transparent source needs none. The checkerboard is only a preview aid, and saved rendering keeps the actual transparency. Whatever is behind your finished frame will show through the gaps. This does not remove the background from an opaque photograph.

Choose **Solid board** and its **Board color** if the strings will have a backing. A blank image matching that board still needs no thread. Set the **longest frame side or circle diameter in centimetres** and **thread diameter in millimetres** before uploading. Frame size and thread diameter affect the coverage simulation. The **Number of Lines** field is a total maximum across all colors, not a quota per color. Generation may stop earlier when it finds no beneficial moves. **Line Weight** continues to apply only to black-string mode, which retains its white background. To regenerate with changed settings, select the same image again.

The result includes:

- A preview made with the same coverage model used by the optimizer and playback.
- A shopping list with color swatches/hex values, path lengths, and suggested purchase lengths. Purchase estimates add **20% plus 1 metre per layer** for wraps and knots; these are planning allowances, not measured consumption.
- Numbered color layers, with explicit tie-on and tie-off pins. Each layer is a continuous path; there is no invisible jump between pins. Tie off and start the next spool at each layer boundary.
- Color-aware **Start Creating**, **Next Step**, **Last Step**, and **Just Draw**. In manual mode, magenta marks the current segment; the text identifies its actual thread color.
- Version 2 saved instructions containing the palette, order, geometry, coverage settings, and paths. Copy the entire text to restore the plan on a fresh page. Version 1 and old comma-separated black-string patterns still work.

### How paths and order are chosen

`color-planner.js` is a dependency-free numerical module shared by the worker, rendering, and tests. Automatic color mode does not depend on NumJS or OpenCV. Work runs in `color-worker.js`, so the page stays interactive and **Cancel color planning** can stop it. Generation supports up to 500 pin numbers and 10,000 total lines. A bounded cache and an image with a longest working dimension of **320 pixels** limit the search. A 4:3 image now uses 320 × 240 working pixels, four times the cells of the previous 160 × 120 grid. This retains finer source detail and pin placement at the cost of more computation and memory. Smaller inputs are not enlarged. Physical frame and thread dimensions still determine coverage at the working resolution.

Saved plans retain their recorded working size and coverage during playback, so existing 160-pixel plans are not silently changed. New 320-pixel plans require the updated app; older releases reject working dimensions above 200. Re-upload the source to generate paths at the higher resolution. Raw error totals depend on working dimensions, so compare plans at the same evaluation resolution rather than comparing their saved totals directly.

The planner clusters visible image colors in display RGB to seed its initial palette. Every cluster is fitted before choosing a weighted median for each channel, so mixed edge pixels have less influence on a small object's thread color. Open-frame plans include white and other light colors on the same basis as dark colors; transparent source pixels contribute no color and partially transparent pixels are weighted by their opacity. On a solid board, pixels matching the bare background do not need thread at this stage, but **the board color is also considered as actual thread after the other paths exist**. For a broad tonal range and more than one allowed color, the 2nd brightness percentile can deepen an existing dark cluster, with an allowance for 2% background showing through on solid boards. It cannot replace a midtone hue or brighten a small dark cluster to a global percentile. This avoids freezing an olive branch's mixed blue-green fringe as its thread color.

The planner compares short trial plans for the selected palette order, light-first and dark-first orders, then generates the full plan using the best trial order. Once the paths exist, it evaluates **all permutations of the used layers** (at most 120). This is a heuristic search, not proof of a globally optimal palette or winding.

Colors compete for a **shared line budget**. The planner repeatedly compares the next useful moves for every color and gives a short batch of windings to the best candidate. It evaluates each insertion in its final layer position, including coverage from later colors. A dark thread can receive most of the windings if that best serves the image; colors do not receive equal quotas. Every spool retains a continuous path, even though the search revisits colors while building the plan.

**Color allocation → Region boundaries (experimental)** instead reserves an initial share for each color in proportion to its patches' combined internal perimeter. A temporary nearest-palette map measures these regions; the image used for scoring is not posterized. One conservative majority pass cleans ambiguous mixed-color fringe pixels while preserving close palette matches, including thin stems and tiny eyes. Horizontal and vertical pixel interfaces approximate perimeter, shared boundaries count for both colors, and the outer frame is excluded. Transparent regions reserve no thread; partially transparent regions contribute in proportion to alpha. Uniform images fall back to visible area because they have no internal boundaries. Largest-remainder rounding keeps integer reservations within the exact total, including pilot plans.

Reservations prioritize useful paths; they never force a net-harmful move. When the remaining reservations cannot be spent usefully, other spools can use the spare budget. Refinement and board-color repair can also change the final counts. Saved `stats.allocation` records the method and, in perimeter mode, each candidate color's perimeter, target lines and actual lines, including colors that received no paths. **Overall likeness remains the default:** perimeter alone can overfund fine feather divisions and underfund broad regions, and it does not recognize the semantic importance of an eye or guarantee that every patch survives. The numerical API selects the experiment with `colorAllocation: 'perimeter'`; omitting it or using `'adaptive'` selects the usual shared-gain allocation.

Each segment is scored by the **reduction in squared display-RGB pixel error plus boundary error**, including both improved and damaged pixels. Local contrast still gives outlines and small features a bounded extra pixel weight, normalized to an average of one. The separate boundary term compares **signed RGB differences** between nearby source pixels and their rendered counterparts. Blurring a gray-on-white seam, reversing its contrast, or overwriting a leaf edge therefore has an explicit cost, even when average colors remain close.

Boundary pairs span two working pixels horizontally or vertically (one on a two-pixel-wide or tall image). Only source pairs with at least 4% display-RGB RMS contrast are retained, and their squared contrast error has a weight of 2. These are fixed heuristics. Candidate scoring includes pairs with either endpoint touched by a string, counts each pair once, and includes the actual coverage from later layers. Path selection, lookahead, allocation, layer-order comparisons and refinement all use this same objective. Small thread-length and repeated-route buildup costs remain even if a route is later covered. When a greedy path stalls, and periodically during the search, a four-candidate, two-move lookahead can accept a harmful first move if the complete connected pair has positive net value. It never commits a harmful half-pair at the line-budget boundary.

Rectangular plans now allow **travel between nearby pins on the same frame side**, bypassing the minimum pin separation used for interior chords. The bounded lookahead also tries up to four nearest edge routes alongside its four ordinary candidates, so a short transit can unlock a better interior stroke even when the transit itself loses value. A transit never rounds a corner, jumps between sides or cuts the spool; coincident corner aliases are not distinct nails. Its visible effect, thread length, buildup and winding count all remain charged. Playback labels these steps “Along the bottom/right/top/left edge.” Circle behavior and saved rendering are unchanged. This is a limited local search, not an exhaustive search of every transit-plus-stroke combination. Numerical experiments can disable the added search with `edgeTravel: false`.

Boundary scoring rewards preserving visible source contrast; it does not recognize objects or create a dividing line where the source has none. Narrow features can still be lost when each available string crosses other parts of the picture, or when later colors cover them. It improves the tradeoff within the available pins, colors and windings rather than guaranteeing a faithful outline.

For transparent plans, each working pixel also tracks **thread coverage (alpha)** alongside premultiplied linear RGB. The objective averages the error of the source and the simulated strings composited on **both black and white backdrops**. This scores missing coverage as well as color: empty space cannot stand in for white or black thread. It is a two-backdrop approximation, not a promise of identical appearance in all surroundings. Source alpha survives image preparation, and path lookahead, later-layer coverage, allocation and refinement all use the same alpha model. Reconstructing an opaque photograph without a backing can require substantially more thread than using a solid board; a fixed line budget may leave considerable transparency.

A refinement pass rebuilds each earlier color with the later windings fixed. Their actual paths form a per-pixel coverage transform, so an early travel segment can receive a discount for later coverage. A replacement is retained only if it improves the complete plan's image-and-material objective. The finished order is compared again after refinement. Colors are wound once each in this version; switching repeatedly between spools and larger lookahead searches are not implemented.

For solid boards, the planner then checks a spool matching the board color: for example, **white thread can restore highlights covered by darker string even on a white board**. It tries adding the spool when colors and lines remain, and replacing each existing spool to free a color slot and winding budget. Each trial winds a continuous path over the retained layers. It is accepted only when the completed image-and-material objective improves, including the cost of losing the replaced color. The final layer order is compared again. This keeps both user limits, does not force white into every shopping list, and still leaves a blank image matching its board with no windings. This pass does not redistribute individual windings between retained spools or guarantee an optimal palette.

The preview uses **partial pixel coverage in linear light**, with later threads covering a fraction of the earlier appearance. It is an approximation of thin opaque threads viewed from a distance, not additive screen-light mixing. It cannot predict the exact placement of adjacent threads, physical stacking, shadows, gloss, or the effect of substituting a different thread color. Coverage is derived from thread diameter relative to the working pixel size, bounded to 0.1–95% per pass. It intentionally never assumes a later thread perfectly hides earlier travel.

Existing version 2 instructions retain their original rendering. Solid-board plans use `render.model: "linear-coverage-v1"`. Transparent plans use `background: "transparent"` and `render.model: "linear-coverage-alpha-v1"`; the updated app is required to replay them. New plans record `stats.errorMetric: "detail-boundary-srgb-two-backdrops-v1"` for transparent frames or `"detail-boundary-srgb-v1"` for solid boards. `stats.finalError` is the sum of the separately recorded `pixelError` and weighted `boundaryError`; material costs are excluded from these diagnostics. Both components use the same black/white backdrop average for transparent plans. Errors from different metrics cannot be compared directly. Re-upload the source image to generate new paths with the palette and boundary improvements. The line limit is a work budget, and stopping early only means the bounded search found no further useful moves; it does not establish a global maximum for a color.

### Color verification

`node --test tests/*.test.cjs` covers net damage, discounted but nonzero covered-travel damage, beneficial connected lookahead, length/buildup penalties, actual layer-order comparison, automatic palette selection, shared line allocation, geometry, JSON replay, physical length scaling, and malformed plans, alongside the existing monochrome regressions. It also checks white and black board colors used as covering thread, replacement within a full palette, rejection of harmful background thread, and recovery of bright details while blank images still need no string. A procedural tonal-detail fixture checks that dark centers remain distinct inside colored rings and bounds the rendered color error. No user photograph is included in the test data.

CI also runs `node --test tests/browser/*.cjs` with Playwright and Chromium. These tests serve the actual page and worker, block external CDNs to verify color mode is independent of them, and exercise upload, generation, shopping lists, pixel-identical automatic playback, fresh-session restore, manual navigation, cancellation, invalid-input recovery, portrait layout, and switching back to legacy instructions.

Transparent-background regressions additionally check default white-thread selection, empty and partially transparent sources, area averaging without a matte, independently calculated overlap alpha and composite error, lookahead rollback, shared allocation, saved replay, and rejection of incompatible background/model pairs. Browser checks cover the default background control, real canvas alpha, transparent uploads, optional solid boards and removal of the checkerboard when returning to legacy playback.

Palette and boundary regressions cover a small olive region with mixed fringe pixels, a rare dark color, preserved versus blurred or reversed gray seams, and path selection between equally useful interior and boundary strokes. Independently calculated full composites check incremental boundary gains on solid and transparent frames, including unchanged neighbors and fixed later windings.

Region-allocation regressions use hand-counted stem, square and eye outlines, transparent and board regions, exact integer budgets, useful reservations, and transfer when a color stalls. A physical rectangle fixture demonstrates a stroke reachable through a same-side transit but not the original bounded search, rejects a harmful unfinished transit, and checks continuous replay and independent length calculations. Browser checks exercise the allocation selector through the worker and label edge travel during saved playback.
